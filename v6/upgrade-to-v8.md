- **New expenses/income always defaulted to INR regardless of base currency — found and fixed 2026-09-24, while testing Epic B Phase 2 with a real second (CAD) account**: `ExpenseForm`/`IncomeForm` hardcoded `currency: 'INR'` as the starting value for every new entry, completely independent of the signed-in user's `baseCurrency` setting. Predates Epic B entirely — invisible until now because every real user of this app so far has been INR-based, where the wrong default happened to be the right value. Fixed: both forms now default `currency`/`conversionRate` to the user's `baseCurrency` (looked up from `rateData.rates`, same INR-relative table `onCurrencyChange` already uses), not a hardcoded INR — `ExpenseForm`/`IncomeForm` gained a `baseCurrency` prop for this. **Worth a second look**: this was found via the household combined-view card specifically, but it affects every entry point in the app, not just household-tagged expenses — if other non-INR base-currency issues surface later, check whether they trace back to this same "amounts are stored/aggregated in INR everywhere, `fmtINR` only relabels rather than converts" pattern before assuming a new bug.

- **Biometric enrollment on iPad — three bugs found and fixed 2026-09-24, pending user verification**: reproduced immediately (user hit "Biometric cancelled or not available on this device" enrolling on a Face-ID-only iPad). Each fix unblocked the next failure point rather than solving it outright — a real three-layer bug, not one bug misdiagnosed three times:

A cold Lambda response pushes `startRegistration()` past iOS Safari's user-activation window, so the browser silently rejects with `NotAllowedError` before any prompt shows. Fixed: GET-warmup early-return + a mount-effect ping in `BiometricSettings`.
  2. **`residentKey: 'preferred'` was requesting a discoverable system passkey**, which is what triggers iOS's "choose how to manage passkeys" picker (iCloud Keychain vs Brave, vs the Passwords app). The app's *authentication* flow never uses discoverable lookup (`biometric-auth-options.js` always passes an explicit `allowCredentials` list), so this was pure unneeded friction. Changed to `residentKey: 'discouraged'` — reduced but didn't fully eliminate the picker on this user's device; enabling `Settings → General → AutoFill & Passwords → Passwords` (Apple's own Passwords app, as the picker itself instructed) was still needed on top of the code fix to get the ceremony to proceed. Sent the user down an unnecessary iCloud Keychain / 2FA troubleshooting detour before landing on this — worth remembering the picker is a `residentKey`/AutoFill-provider issue, not an account-configuration one, if it recurs.
  3. **`registration_challenges` pile-up, the real blocker underneath both of the above**: `biometric-register-options.js` wrote each new challenge via `.upsert({user_id, ...})` with no explicit `onConflict` target, which falls back to the table's primary key — not confirmed to be `user_id` in this codebase's tracked migrations (this table predates the `supabase/add_*.sql` convention, no migration file exists for it). Every attempt across the whole debugging session — cold-start fails, cancelled passkey prompts, all of it — was very likely inserting a fresh row instead of replacing the old one. The completion endpoint's `.select(...).eq('user_id', user.id).single()` requires exactly one row; once 2+ existed, every future attempt failed with "No challenge found — restart enrollment," sending the user back to retry, which piled on yet another row. Self-reinforcing — this is almost certainly what "keeps looping back" was. Fixed: explicit delete-then-insert instead of upsert, which self-heals any rows already piled up on the very next attempt (no manual DB cleanup needed).
  - All three code fixes are real and shipped, but enrollment on this specific iPad is still blocked by a **device-side (not app-side) root cause**, found by process of elimination through Settings: same Apple ID on both devices ✓, 2FA on + both devices trusted ✓, no Screen Time/Content & Privacy restriction or MDM profile ✓ — but the iPad was **set up as new** (not restored from the iPhone's backup), so it never inherited iCloud Keychain participation. Per Apple's own docs, turning on Keychain sync on a new device sends a **circle-of-trust approval request to the user's other trusted devices** (a notification on the iPhone), which has to be explicitly approved there before the new device's Keychain actually activates — this approval step was likely missed/never completed, explaining why "Sync this iPad" was already toggled on yet iCloud Keychain still never appeared in the AutoFill provider list. Only Brave shows as a provider because it's the only one that's actually functional on that device.

# Epic A — Personalization ("your things" tracking)

## Context

The user wants a dedicated personalization area where they register the actual things in their life that expenses relate to — cars/bikes, credit cards, maybe more than one house, phones — "as detailed as we can make it." Today the app has no concept of any of this: fuel/maintenance fields exist on expenses but aren't tied to a specific vehicle, and there's no personal-asset registry at all.

This lives as **one new section inside the existing Settings page** (Settings is a single long scroll of `.settings-section` blocks today — App Update, Appearance, Base Currency, Data stats, Safe-to-Spend, Exchange rates, Notifications, Export, Import, V5 Migration, About, all in `src/components/Tracker.jsx` inside `tab === 'settings'`). No new tab, no modal — a new "🏠 Personalize" block joins that same stack, with pills inside it to switch between asset types (Vehicles / Credit Cards / Houses / Phones / …).

**Architecture decision**: this codebase's convention is one dedicated Supabase table per feature (trips, goals, budgets each have their own typed table — no generic entity/EAV table exists anywhere). Keep that convention: each asset type gets its own table with real typed columns, built one phase at a time, using Vehicles as the template to clone for the rest. But to avoid bolting a new `_id` column onto `expenses` every time a new asset type ships, expenses link to *any* asset through one generic pair of columns: `asset_type text` + `asset_id text` (e.g. `('vehicle', 'v_abc123')`), set once now, reused by every future phase — no further `expenses` schema changes needed as new asset types are added. **Epic B reuses this exact lightweight-tagging technique** (a nullable `household_id` column) for linking expenses to a household, so the pattern pays off twice.

A second shared building block: a generic `.ics` calendar-reminder download helper (Blob-download, same pattern as existing JSON/CSV export) — needed for PUC renewal (vehicles), card due-date (credit cards), rent due (houses), and warranty expiry (phones), so it's written once, generically, now.

## Shared infrastructure (build once, used by every phase)

1. **`expenses` gets two generic columns**: `alter table expenses add column if not exists asset_type text, add column if not exists asset_id text;` — no FK constraint (matches the no-FK precedent already used for trips-to-expenses date matching). App schema: `asset_type`/`assetId` added to `makeExpense()` (`src/utils/dataHelpers.js`) and `expenseToDb`/`expenseFromDb` (`src/hooks/useStorage.js` lines 14-99).
2. **Generic `.ics` reminder helper** in `Tracker.jsx`, near the existing Blob-download handlers (`handleExportJSON`/`handleExportCSV`, lines 2117-2154):
   ```js
   const downloadIcsReminder = ({ uid, date, summary, description, alarmDaysBefore = 3 }) => {
     const dt = (date || '').replace(/-/g, '')
     if (!dt) return
     const ics = [
       'BEGIN:VCALENDAR', 'VERSION:2.0', 'PRODID:-//ExpenseTracker//Reminder//EN',
       'BEGIN:VEVENT', `UID:${uid}@expense-tracker`,
       `DTSTAMP:${new Date().toISOString().replace(/[-:]/g,'').split('.')[0]}Z`,
       `DTSTART;VALUE=DATE:${dt}`, `DTEND;VALUE=DATE:${dt}`,
       `SUMMARY:${summary}`, `DESCRIPTION:${description}`,
       'BEGIN:VALARM', `TRIGGER:-P${alarmDaysBefore}D`, 'ACTION:DISPLAY', `DESCRIPTION:${summary}`, 'END:VALARM',
       'END:VEVENT', 'END:VCALENDAR',
     ].join('\r\n')
     const blob = new Blob([ics], { type: 'text/calendar' })
     const url  = URL.createObjectURL(blob)
     const a = document.createElement('a'); a.href = url; a.download = `${uid}.ics`; a.click()
     URL.revokeObjectURL(url)
   }
   ```
   `\r\n` + `VALUE=DATE` per RFC 5545 — Outlook/Apple Calendar are strict about CRLF. No library needed. Called by each phase with its own `uid`/`date`/`summary`.
3. **"Personalize" modal shell, revised from an inline settings-section**: Settings has just a launcher row ("Open Personalize" button); clicking it opens a `PersonalizeModal` component reusing the exact same `.modal-overlay`/`.modal`/`.modal-header` pattern already used by `ExpenseForm`/`NewGoalModal` — not a new bespoke popup mechanism. Inside the modal, the pill/tab row (Vehicles | Credit Cards | Houses | Phones) switches which asset-type's card-list + form renders below. Rationale: Settings is a scroll of lightweight toggles; Personalize will get heavy (forms, card grids, metrics per asset type) once fully built, so it earns its own focused surface rather than living inline. Each phase below adds its own pill + table + CRUD; the shell itself doesn't hardcode a specific type. (Implemented in Phase 0 as a simple modal without drag-to-dismiss, matching `NewGoalModal`'s lighter pattern rather than `ExpenseForm`'s `useBottomSheet` — revisit if Vehicles' eventual form content needs the fuller sheet treatment on mobile.)

# Epic B — Household & Multi-User Support

**⚠️ Review after all of Epic B (Phases 0-3) is complete**: as built, a `connections` row carries no relationship label at all — Connections just shows the other person's name/email, nothing about *how* they relate to you (spouse/child/friend/etc). Raised while testing Phase 0 (2026-09-24); decision was to hold off and look at the full picture — Households (Phase 1) already gives named groups + roles, which may cover this well enough on its own. Revisit once Phase 3 ships: does the household name/role already answer "how is this person related to me," or is a standalone per-connection label (e.g. a private free-text field, "Wife"/"Brother", each side can set their own independently) still worth adding on top?

## Context

The app is currently strictly single-user: every table's RLS policy is `auth.uid() = user_id` with zero sharing mechanism anywhere, signup is self-serve magic-link with no invite/allowlist, and the existing `splitWith`/`splitParts` fields are pure free-text memo labels with no connection to a real account. The user wants to eventually hand this app to their wife and family members, track personal (private) expenses alongside household/family combined expenses, and split costs with people — some of whom are close family (a formal "household" with a combined dashboard) and some of whom are just individually-invited friends (for one-off splits, not part of any household), with real running-balance settlement for anyone who has an account, same as today's free-text fallback for anyone who doesn't.

**Decisions locked in with the user:**
- **Invites**: one generic invite-code system for everything. Owner generates/shares a code; recipient signs up via the existing magic-link flow and redeems the code once. Redeeming creates a **connection** between the two users — NOT automatic household membership. Adding a connection to a household, or just keeping them as a split-only "friend," is an explicit second step taken after the connection exists.
- **Households**: named group, owner + co-owner roles (ownership transferable, multiple co-owners allowed), at least one owner must always remain. Only existing connections of a current member can be added — no adding strangers directly.
- **Sharing model**: private by default. An expense/income row can be explicitly tagged to a household (nullable `household_id`, reusing the exact lightweight-tagging pattern from Epic A's `asset_type`/`asset_id`), making it visible (read-only) to that household's members for a combined view. Row ownership/edit rights never change — only extra SELECT visibility.
- **Splits**: generalize today's free-text `splitWith` into real participants — each one is either a connected real app user (household member or friend connection) or a free-text external name (today's behavior, kept as the no-account fallback). Real connected-user splits get full running-balance tracking and settle-up (Splitwise-style, not just a static share calculation); free-text participants stay informational-only (no counterpart account to settle with).

This is a large, security-sensitive change (RLS rewrite touching most tables), now fully designed and verified against the actual codebase (spot-checked: `expenseFromDb` in `useStorage.js:57-99` really is missing a `userId` mapping needed for Phase 3's balance calc; split UI confirmed at `Tracker.jsx:1310-1317`; biometric lock confirmed single-account via singular `localStorage` keys in `useBiometric.js:5-9`).

## Cross-cutting decisions (apply to every phase below)

- **New prerequisite: `profiles` table (built in Phase 0).** `auth.users.user_metadata` is JSONB that client-side RLS-joined queries can't reach — connections/households/splits all need to resolve a `user_id` into a display name for UI ("X owes Y") and need RLS policies that join across users. A `public.profiles` table (`id uuid pk → auth.users`, `display_name`, `email`), populated by an `auth.users` insert trigger, is the standard Supabase pattern and a hard requirement, not optional polish.
- **RLS recursion avoidance, general rule**: never let table A's policy subquery table B if B's policy subqueries A back. `households`/`household_members` mutual visibility uses `security definer` helper functions (`is_household_member`, `is_household_owner`) instead of nested policy subqueries — the function reads with RLS bypassed internally, so the policy itself never recurses. `expense_splits` → `expenses` stays one-directional (expenses' own policies never reference `expense_splits`), so no cycle there either.
- **Biometric lock's single-account-per-browser assumption is a known, unfixed gap.** If two household members share one physical device, the second person's biometric enrollment overwrites the first's `localStorage` keys, silently locking the first out of biometric unlock (falls back to magic-link, not broken, just degraded). Out of scope for this epic — revisit only if shared-device usage actually gets reported.
- **No new onboarding-wizard step for invites.** Redeeming a code is a post-onboarding action: support an optional `?invite=CODE` URL param that `Auth.jsx` stashes in `sessionStorage` before the magic-link redirect, then auto-prompt to redeem once onboarding completes; plus an always-available manual redeem field in Settings. Matches the existing wizard's own skip-everything bias — most signups are organic, not invited.
- **ID column convention, corrected**: every new table's primary key is `id text primary key`, client-generated the same way `addExpense`/`createHousehold` already do (`Date.now().toString(36) + Math.random().toString(36).slice(2)`) — matches every existing table (`expenses`, `trips`, `goals`, `vehicles`) and is *required* for this codebase's optimistic-UI pattern, since the client must know the row's id before the insert response comes back to show it immediately with `_pending: true`. The one deliberate exception is `profiles.id`, which is `uuid` because it must equal `auth.users.id` (always uuid) — that's not an inconsistency, it's a hard requirement. `invites`, `connections`, and `expense_splits` below are corrected from an earlier `uuid default gen_random_uuid()` draft to `text`, client-generated, to match.

**Bug found and fixed post-ship, 2026-09-24, while user-testing Phase 1 (not Phase 2 itself)**: `createHousehold()`'s first insert (`households`) used `.select().single()`, i.e. `INSERT ... RETURNING *`. Postgres requires a RETURNING row to also satisfy the table's **SELECT** policy, not just the INSERT policy's `WITH CHECK` — and the `households` SELECT policy (`is_household_member`) depends on the owner's `household_members` row, which only gets created in the *second*, separate insert right after. So the first insert's RETURNING clause failed the implicit SELECT check every time, with the exact same error text ("new row violates row-level security policy") as a broken `WITH CHECK` — a red herring that took a decoded JWT + a raw request-payload comparison to rule out before finding the real cause. Fixed by dropping `.select()` from that one insert (the client already knows the full row locally, so there's nothing to gain from RETURNING). **Same risk applies to Phase 3's `expense_splits` insert** — its SELECT policy depends on either the payer or the participant, so any insert there using `.select()`/RETURNING needs to be checked against this exact trap before assuming a "policy violation" error means the policy itself is wrong.

**Deeper bug found and fixed same day, while user-testing the combined household view itself**: the plan's documented "known gap" ("realtime isn't instant, but refetch/tab-switch is correct") was wrong — it undersold the actual bug. The initial-load query for `expenses`/`income` is `.eq('user_id', userId)`, which is *more restrictive* than RLS — a household member's client never fetched another member's household-tagged rows **at all**, not even on reload, because the client-side filter excluded them before RLS was ever consulted. **The leak this fix was designed to avoid happened anyway, same day, through a path I hadn't checked**: `supabase/add_insight_views.sql`'s three views (`v_monthly_expenses`/`v_monthly_income`/`v_yearly_expenses`, powering Analytics → Trends) have no `WHERE user_id = ...` of their own — they're `security_invoker = true` and rely entirely on `expenses`/`income`'s RLS SELECT policy to scope rows. **Currency conversion gap — three rounds before finding the actual root cause, fixed same day**: `fmtINR()`, despite the name, only applied the current base currency's symbol/locale to whatever raw number it's given — it never actually converted. This was app-wide, not scoped to Epic B, and each fix revealed the next layer:
1. `ExpenseForm`/`IncomeForm` hardcoded `currency: 'INR'` for every new entry regardless of the user's `baseCurrency` — invisible until now because every real user so far has been INR-based. Fixed: both default to `baseCurrency` instead.
2. `householdViewData`'s combined-view totals were computed correctly in INR internally but rendered via `fmtINR()` with no conversion step. First fix: converted manually inside the memo before formatting.
3. **The real root cause, found when the identical symptom showed up in the plain private expense list** (not just the household card): `ExpItem`/`IncItem` — the shared row component used *everywhere* in the app — call `fmtINR(toINR(item))` the same unconverted way. This meant the bug was never actually specific to Epic B's household view; it was the shared formatter itself, used in ~165 places throughout `Tracker.jsx`. Fixed at the root instead of patching more call sites one at a time: `_fmtINR` now divides by a module-level `_appRate` (INR-per-1-baseCurrency, kept in sync via a `useEffect` alongside the existing `_appCurrency` sync) before formatting, so every caller that passes an INR-aggregated figure — which is the codebase's universal convention (`toINR()`/`amountINR`) — now converts correctly app-wide. Reverted the household card's own manual conversion from fix #2 once the root fix landed, since doing both would have silently double-divided. Two call sites needed a companion fix because they passed a *not-yet-INR* raw form value into the now-stricter `fmtINR`: the expense-split "Your share" preview (converts `form.amount` through `form.conversionRate` first now) and the "INR Equivalent" form preview label, which is relabeled to `{baseCurrency} Equivalent` since it now genuinely shows the base-currency amount, not literal INR.

**Lesson for future currency-adjacent bugs**: when a display bug shows the identical symptom in two unrelated-looking places (household card, then the plain private list), stop patching the second location and go find the shared function underneath both — that's almost always the actual root cause, not a coincidence.

4. **A fourth, deeper layer the user caught by asking "why should a CAD user ever need to think about INR at all":** even with fix #3, a same-currency item (CAD entry, CAD base currency) was still being needlessly round-tripped through the INR pivot for display — converted to INR at entry time (that day's rate), then back to CAD at view time (today's rate), silently drifting the shown amount away from what was actually entered purely from rate movement between the two, despite nothing about the expense changing. `toINR()` already special-cased `currency === 'INR'` to skip conversion entirely, which is exactly why this was invisible for INR-base users — there was just no equivalent special-case for "item's currency matches *my* base currency" when that base currency isn't INR. Fixed with a new `fmtExact(amount, currencyCode)` helper (format a raw amount in its own currency, no conversion at all) used by `ExpItem`/`IncItem` whenever `item.currency === _appCurrency` — the exact original amount, zero rate-drift risk. Also fixed the matching form-side symptom the user originally reported ("shows a converter to INR" when entering a personal expense): `isForeign` in `ExpenseForm`/`IncomeForm` was hardcoded to `currency !== 'INR'` rather than `currency !== baseCurrency`, so a CAD user entering CAD saw an unnecessary rate input + conversion preview. - [x] **Country-specific calculation methods (added 2026-09-19 per user request)**: user wants to "replicate exactly how banks of each country do it," not just a cosmetic region label. `debts.rate_method` (`'monthly' | 'daily' | 'canadian'`, own migration column) drives the actual periodic-rate math in `generateSchedule()`/`calcMonthlyPayment()`:
  - **Monthly** (US & most conventional loans) — flat `annual/12`, unchanged from the original implementation.
  - **Daily** (India, UK, Australia home loans) — interest accrues on the actual outstanding balance × actual calendar days in that month ÷ actual days in that year (365/366, leap-year aware) — needs the debt's `startDate` for real calendar dates, falls back to Monthly if it's missing. The EMI amount itself is still set via the standard monthly formula (matches real bank practice — daily accrual affects interest apportionment, not the fixed installment).
  - **Canadian** — the Interest Act mandates interest compounded semi-annually even though payments are monthly, so the periodic rate is `(1 + annualRate/200)^(1/6) − 1`, not a flat `annual/12`. This changes the EMI amount itself (verified: $200k @ 5% over 25yr gives $1,163.21/mo under Canadian rules vs $1,169.18/mo under naive-monthly — Canadian mortgages are genuinely slightly cheaper per month at the same posted nominal rate, a well-documented real quirk of semi-annual compounding).
  - Debt form gets a "Calculation Method" dropdown, defaulting by the app's base currency (INR/GBP → Daily, CAD → Canadian, else Monthly) but overridable per debt — modeled as a property of the *loan*, not the user's region, since a user could hold loans from multiple countries at once
- [x] **EMI due-day + reminder (added 2026-09-19 per user request)**: `debts.emi_due_day` (day-of-month, same pattern as `credit_cards.due_day`) drives two things — the "Mark [X]'s EMI paid" button now labels itself from the real next due date (`nextDueDateFor(emiDueDay)`, always grounded in today's actual calendar, not the schedule-position projection used by `nextDueLabel`/part-payment date defaults) and a "📅 Download EMI reminder" button (reuses the existing `downloadIcsReminder()` helper, same as Vehicles/Credit Cards/Houses/Other Assets). ## Known risks (Epic C)

1. **C1 projections are only as good as the assumption inputs** — a 30-year compound projection off a 30-day spending sample is inherently rough; the UI disclaimer matters, not just the math.
2. **C2 amortization math must be tested against a known reference** (e.g. a public loan calculator) before trusting the "interest saved" numbers — a formula transcription bug here gives the user wrong financial advice, worth one careful cross-check.
3. **C3 rule ordering matters** — first-match-wins means rule priority order directly changes behavior; needs clear UI feedback about which rule fired on a given expense (the "✨ auto-applied by rule" hint should say *which* rule, not just that one fired).
4. **No shared infrastructure between C1/C2/C3** — unlike Epic A's `asset_type`/`asset_id` reuse, these three are independent; fine to build in any order or skip one without blocking the others.
